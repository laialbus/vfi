# 2026-08-29 — M4-07

Branch `M4-07`. `vfi_fetch::company_facts` retrieves a filer's XBRL company
facts by CIK and hands back the boundary's own `Filer`, built from the type
`vfi-contracts` publishes. One request per filer, out through `Egress` like
every other. Nothing is filtered — every taxonomy, tag, unit and form crosses —
and nothing is parsed: an amount is read as raw JSON and carried as the
characters EDGAR published, which is why the crate now takes `serde_json`'s
`raw_value`. Facts leave ordered by the keys they were nested under, because the
document's objects have no order and a list does.

`Cik::new` is public now. A retrieval keyed by a CIK is unusable to a caller who
holds EDGAR's key and no document to read it out of.

Fixture `every-fact-a-filer-reported`: CIK 0002003750, 1643 facts, recorded
through `crates/fetch/src/bin/record.rs`. Why that filer, and what a second
facts case should differ in, is in the harness header beside the case shape it
describes. `expected` was written from the recording by a throwaway reader that
is not this crate. The harness gained the `cik` case shape and the five-field
uniqueness check the accepted record left to the first fixture; proved by hand
both ways — a planted second value under one identity is reported with both
values and neither chosen, and a fact removed from the recording turns the case
red. The recorded document holds no collision, so nothing is escalated.

For the decider. The one recording command ran with the sandbox off, as M3-10's
did and for the same reason: sec.gov is not in the shell allowlist, the task
mandates a live recording, and `Https` reaches only the host the engine's own
list clears. Nothing else in the run did. Two recordings taken minutes apart
were byte-identical.
