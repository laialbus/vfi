# Escalation: M2-14

- Date: 2026-08-07
- Branch: M2-14

Two of M2-14's acceptance criteria cannot both hold, and one had to yield.

"A task whose id does not match its filename" must refuse. "Nothing proved gets
narrower; every existing case still passes" must also hold. The corpus case
`release-of-an-id-with-a-slash` pins a queue holding `tasks/M1-01.md` with
`id: escalated/M1-01-swept-…`, and pins `release` of that id being refused by
`own_branch_only` — the guard that keeps an archive branch out of reach of the
thing that deletes refs. The new naming rule refuses that queue at the read,
before any subcommand acts on it, so the case cannot keep its old outcome.

I took the naming rule, because the task names it explicitly and its body names
the mistake it catches ("a copy-pasted id"). The case now pins the refusal at
the queue read. Everything else is delivered and every gate passes.

What this costs: `own_branch_only` is now unreachable. An id with a slash can
only enter through a task file, and no file matching `tasks/*.md` is named for
one, so the queue read refuses it first; `sweep` and `release` both take their
ids from the queue. The guard is left in place, cheap and no longer exercised by
anything.

To resolve: decide whether an unreachable guard with no case behind it should
stay, be deleted, or be pinned some other way — and, if the answer is "stay",
whether a run may leave a guard uncovered when a wider rule subsumes it, since
the same shape will recur. Nothing is blocked meanwhile.
