# Escalation: M1-08

- Date: 2026-08-01
- Branch: M1-08
- Commit: 2a86248

The installed protect-paths hook refuses nothing on this machine, and has not
since it was installed in PR #20.

M1-08 required a read confirming the installed copy exists at
`.claude/hooks/protect_paths.py` before draining the draft. It exists and is
byte-identical to the draft, so the task itself proceeded — but the installed
copy does not run. `.claude/settings.json` invokes it as `python3`, which here
is `/usr/bin/python3`, Python 3.9.6. Line 158 evaluates
`span: tuple[int, int] | None` at class-definition time, and PEP 604 unions on
builtin generics need 3.10, so the file raises `TypeError` on import and the
process exits 1. Claude Code blocks only on exit 2. Every tool call is
therefore allowed, including the writes to protected paths that this hook is
the enforcement for. AGENTS.md names it the second of three layers containing a
run; that layer is currently open. Layers 1 and 3, the OS sandbox and branch
protection, are unaffected.

Confirmed two ways: feeding the hook an ordinary tool call prints the traceback
and exits 1, and this run's own Bash command naming a protected path inside an
interpreter invocation was not refused.

The guard's logic is sound — it is only unreachable. Under `python3.12`, which
is present on this machine, `docs/proposals/protect_paths_tests.py` passes all
93 cases and exits 0.

I cannot fix it: both candidate fixes land in protected paths — adding
`from __future__ import annotations` to the hook, or pinning a 3.10+
interpreter in `.claude/settings.json` — and either is outside this task's
`owns` and needs human sign-off in an ADR. Choosing between them is the
decision I need. Pinning an interpreter states the requirement where the
invocation is; the `__future__` import keeps the hook running on whatever
`python3` a machine has, which is the property that failed here.

Related, and not fixed for the same one-task rule: the corpus harness reads any
exit code other than 2 as `allow`. Run under 3.9 it reported the crash as 57
ordinary case failures rather than a hook that never ran, so the harness turned
a dead guard into a merely permissive-looking one. It should treat an exit
outside {0, 2} as an error. That is a change to
`docs/proposals/protect_paths_tests.py`, and it wants its own task, together
with the two other things that file now states wrongly: its header still ties
its installation to a draft this branch drained, and it still reads its
candidate from a sibling that is gone. The README records the current
condition; the file itself does not.

Worth re-running the corpus under a 3.10+ interpreter after the fix. It cannot
have been green on this machine's `python3` when PR #20 installed the hook, so
it either ran on a different interpreter or did not run.
