GOALS.md's first M5 criterion says the key "reaches the engine only as a
parameter", and ANCHORS.md says the engine "never reads a keychain, config
file, or environment for one". `docs/adr/price-provider.md` is accepted, and it
designs the parameter. Under Enforcement it then says nothing stops `vfi-fetch`
reading `std::env` or a file for a key, that M5-04's check reads only
`crates/analyze/`, and that extending a source-name check to the fetch crate
is "a new gate, above this record". Its Decision review says the gap "stands
open, and no queued task holds it". This is the record that holds it.

`docs/adr/TEMPLATE.md` puts a new gate in the Structural tier, so the record
comes before the gate. The task that builds the check is queued under this
record's acceptance and will own `scripts/gates.sh`. The task that implements
the provider waits on that check, because AGENTS.md makes a change with no
gate an escalation.

It depends on M5-04 because the record has to say how its check sits beside
that one, and that one has to be on main to be read.

Main already reads the environment and files inside the engine, for reasons
that are not a key. `crates/fetch/src/bin/record.rs` takes its arguments
through `std::env` and writes files. `crates/fetch/src/ledger/journal/` and
`crates/normalize/src/registry/tree.rs` read files. A check that reads source
for names cannot tell a key file from a journal, which is why what it reads
for is a decision and not a list to copy.

If the work finds it cannot be done without changing something
`price-provider.md` decided, or without narrowing M5-04's check, that is an
escalation.
