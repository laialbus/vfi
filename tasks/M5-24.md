GOALS.md's first M5 criterion says the key "reaches the engine only as a
parameter", and ANCHORS.md says the engine "never reads a keychain, config
file, or environment for one". `docs/adr/no-key-read-by-the-engine.md`,
accepted on 2026-10-10 and on main since #320, is the record for the check
that makes that hold. It decides the gate's name and place, the crates it
reads, the names it shares with `ambient` and the names of its own, the
three key's places and the carve-out for the spent journal, the `keychain`
group, the fourteen plants and the accept copy, and what the gate cannot
see. This task builds exactly that and decides nothing the record leaves
open.

`scripts/gates.sh` is protected and grantable, so this task lists it under
`owns`. The pull request merges only with the `human-approved` label, applied
by a human hand. It runs alone because the gate runner is a shared surface.

It depends on nothing because everything the record reads is on main:
`ambient_names`, `ambient_reaches`, `ambient_crate`, `denied_packages`,
`chokepoint`, `wire_names`, `workspace_members` and `direct_dependencies`
all stand in the runner today. The spent record (M5-25) waits on this,
because `crates/fetch/src/price/` is a key's place and AGENTS.md makes a
change with no gate an escalation; the provider waits on it for the same
reason.

If the gate cannot be built as the record states without writing a shared
name a second time, without an exception for a read main already holds, or
without narrowing what `ambient` reads for, that is an escalation, not a
wider gate.
