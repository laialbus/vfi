`docs/adr/what-analyze-takes-and-returns.md`, accepted on 2026-10-03, fixes
the call: one function, three explicit inputs, one error, nothing kept
between calls. It fixes the method version as `METHOD_VERSION` in
`method.rs`, starting at 1; the settings as one `Settings` type in
`settings/` reached through a preset constructor the caller calls and the
derivation never does; and the premises every result records. It names the
edge `vfi-analyze>vfi-contracts` and says it lands "in the task that first
uses them", under the `human-approved` label. This is that task. GOALS.md's
seventh and eighth M5 criteria, that every free parameter arrives as a
setting and that each result records the settings and method version it was
computed from, are read off this skeleton; every metric task adds to it and
none redefines it.

`scripts/gates.sh` is protected and grantable, so this task lists it under
`owns`, for the one `allowed_edges` line. The pull request merges only with
the `human-approved` label, applied by a human hand. It runs alone because
the gate runner is a shared surface.

It depends on M5-12 because the hand-over is that contract's type, and on
M5-14 because the first file under `settings/` and the first `METHOD_VERSION`
must land under the `literals` gate that reads them, and because both own
`scripts/gates.sh`.

Which crate calls analyze is left open by the accepted record and is not
decided here. Nothing calls the entry point but its own tests.

If the hand-over cannot be built without a choice the record leaves to a
metric's task, or the edge needs anything beyond the one line in
`allowed_edges`, that is an escalation.
