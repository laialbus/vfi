title: A transport that reaches EDGAR, built inside the chokepoint
milestone: M3

acceptance:
  - One implementation of `Transport` that opens a real connection lives under
    `crates/fetch/src/egress/`, which is the one directory the egress gate
    allows a connection to be opened in. Nothing outside it gains a way to
    reach the wire.
  - It connects to the host the chokepoint already read and cleared —
    `Cleared::host()` — rather than reading the URL a second time. Two readings
    of one URL is how the host that was checked and the host that is reached
    come apart, and the chokepoint hands the host over precisely so the second
    reading never happens.
  - Certificates are verified, and no caller-visible way to turn that off
    exists. An allowlist over a connection nobody authenticated names a host
    rather than reaching one.
  - No redirect is followed to a host the list has not cleared. Handing the
    status back unfollowed is enough — a 3xx is already a stated outcome — and
    following one is permitted only by going out through `Egress::fetch` again,
    so the list is read for the new host. What is refused is a client that
    follows a redirect underneath the check.
  - Whatever the source answers is a `Response`, status and body, including the
    statuses that are refusals. Only the wire failing is an `io::Error`. A 403
    from an undeclared client and a 404 for a filing that is not there are
    answers, and the stage above already tells them apart.
  - Every request carries the declaration header the policy names, with the
    value the `Egress` was built with, and nothing added here acquires a second
    path around the pace or the list.
  - The dependency this takes is a direct dependency of `vfi-fetch` alone.
    `vfi-analyze` does not gain it, so the purity gate stays green. The session
    entry names the choice and what was weighed against it, as M3-03 did for
    serde.
  - No test added here reaches the live network. A server the test itself
    starts on loopback is not the live network — the property to hold is that
    the gates give the same answer with the machine offline.
  - Nothing proved gets narrower: every existing gate, proof, and fixture case
    still passes, and the egress gate still counts source both inside the
    chokepoint and outside it.

M3's first criterion is the one still open. Everything the retrieval needs is
built — the ticker map, the submissions document, the overflow pages, the
funnel, the verdicts — and none of it can leave the machine. `lib.rs` says so
outright: "Nothing here reaches a real source yet." Every `impl Transport` in
the tree is in `tests/`, so what the stage has today is a complete description
of a retrieval it cannot perform.

Where this goes is already decided and already written down. `egress/mod.rs`
ends with it: "Code that talks to a real source belongs here, underneath the
check; everything else in the crate belongs outside it, where the ban holds."
The gate enforces exactly that split, so this is the one task whose work
belongs in that directory.

The criterion that carries the weight is the redirect. Every other property
here is about doing the work; that one is about not undoing M3-01. A client
that follows redirects on its own turns the allowlist into a check on the first
hop only, and the host it eventually delivers a body from is one no list ever
saw. The default in most clients is to follow. Choose deliberately, and prove
the choice rather than stating it.

How the transport is proved without a wire is yours. The seam exists — a
`Cleared` is constructible inside the module that defines it — and what needs
proving is what this code does with a redirect, with a status that is not 200,
and with a connection that fails, none of which needs EDGAR to answer.

That it reaches EDGAR at all is M3-10's, which records a fixture through it.
Landing this one unwitnessed is expected; landing it unproved is not.
