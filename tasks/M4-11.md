title: Reach the registry through the one interface normalize owns
milestone: M4
owns:
  - crates/normalize/
  - Cargo.lock
depends_on: [M4-09, M4-10]
exclusive: no
acceptance:
  - '`vfi-normalize` gains exactly one way to reach the registry, in the shape
    `docs/adr/tag-concept-registry.md` fixes: given a filer, its kind and a
    concept, it answers with the eligible rules, each carrying its id, or with
    the value an override asserts for that concept and period, and it names the
    registry version. Nothing about files, directories, TOML, or the way an
    override is written crosses it.'
  - The registry version is the digest the record defines — a sha256 over the
    files under `registry/`, taken in a fixed order over their
    repository-relative paths — so one tree always digests one way. It is
    computed in this one place and nowhere else, and a test pins that the same
    tree digests the same way twice and that a changed byte changes it.
  - Where an assertion covers the filer, the concept and the period, the answer
    is that value, no eligible-rule lookup runs, and the answer carries the
    assertion's own rule id, so an asserted number is visibly asserted rather
    than indistinguishable from a read one.
  - The eligible set for a filer and a concept is the general set for that
    filer's kind, less what the filer's file excludes, plus what it includes,
    and it does not depend on the order the two are written in. A test states
    that independence rather than leaving it to the reading order of a file.
  - A concept with no eligible rule and a concept with no entry at all are
    answered the same way — an attempt that ran and found nothing. The interface
    never answers `NotApplicable`, which the vocabulary makes constructible from
    a filer kind and an applicability clause and from nothing else.
  - A registry the gate would refuse, or an override the gate would refuse,
    fails to load and the stage does not run. It never degrades to an empty
    eligible set and never resolves to `Unknown`, because a data defect hidden
    behind a state that means a filing was consulted is worse than a stop.
  - Where the registry is read from arrives as an input rather than as a path
    the crate assumes, so the engine holds no per-user state and every operation
    takes its inputs explicitly.
  - The interface neither ranks nor chooses among the eligible rules it returns,
    and reads no `form`, `filed` or `accession`. Choosing among candidates and
    reconciling filings across them are separate records, neither of them
    accepted yet, and a preference invented here would be one of them written
    where nobody would look for it.
  - Nothing resolves. No filing is read, the stage still hands its input back
    unchanged, and the normalize golden fixture is unchanged — so the change
    that lands the first resolved value is the change that states a new expected
    result for it.
  - The registry data and the gate over it are not edited, no new workspace
    member is created, and no new edge between stages is permitted or taken.
  - Adding a second consumer of the registry is an ADR, and this diff adds none.
    The gate reads the files as machinery; nothing else in the engine does.
---

Both halves of the registry are data on disk by the time this can be claimed, and
nothing in the engine can read them. The accepted record gives the reader its
shape and its reason in one line — the tag mapping is among the components
ANCHORS.md says are "reached only through an explicit interface," whose internal
shape is private and may change freely. That privacy is what makes the format,
the part of the record most likely to be wrong, the cheapest thing in it to
change later. An interface that leaked a file path or a TOML table would spend
that.

What it answers is deliberately narrower than what a reader might expect it to.
It reports which rules are eligible, not which one wins: entries for a concept
are a set whose order in the file means nothing, and choosing between two that
both match facts in one filing is a separate record that does not exist yet.
Returning them ranked, or returning only one, would be that record decided here
by whoever implements this.

The version is the other half of the job. A resolved value records the pair of
registry version and rule id and never the id alone, because the same id under
two versions may name different bytes. The digest is what pins which, so it is
computed rather than chosen, and computing it in a second place later is how the
two readings begin to disagree.

Not in this diff, and worth naming so the run does not drift into it: resolution.
Mapping a filer's facts into concepts needs the rule that chooses among several
candidates in one filing, and the ruleset that reconciles amendments,
restatements and periods. Both are records still to come. What this task delivers
is the door those will knock on.
